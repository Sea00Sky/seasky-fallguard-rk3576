# 性能与资源实测

板卡是 Kickpi K7C（RK3576）。四个 A53 跑到 2016 MHz，四个 A72 跑到 2208 MHz，
NPU 两个核，可用频率 300 到 950 MHz，DDR 可用 534 到 2736 MHz，CMA 给了 16 MB。
出厂 governor 是 CPU `schedutil`、NPU `rknpu_ondemand`（停在 300 MHz）、
DDR `dmc_ondemand`（停在 534 MHz）。

帧周期的预算是 30 fps 对应 33.33 毫秒一帧。但真正卡住下限的不是这个：覆盖率门
是 0.70，也就是说一条 60 帧的窗至少要有 42 帧检测到这个人才评分，检测段必须稳定
跑在 21 fps 以上，否则窗口凑不齐，召回直接掉。后面所有"过不过门"说的都是 21 fps。

## 一、推理后端

板端有两套后端。一套是 rknnlite 的 Python 包装，接口是 `inference(inputs=[...])`；
另一套是 `board/src/backends/rknn_zerocopy.py`，用 ctypes 直调 librknnrt，自己
管输入输出内存。

生产用的是 FP16 模型，正确喂法是喂 float16 张量并打开 `inputs_pass_through`。
这一点踩过坑：模型的原生输入是 float16/NHWC，喂 float32 且不开直通时，
`set_inputs` 会花 32 毫秒做逐元素转换；喂对之后是 1.7 毫秒，差 19 倍。

同一批帧上两套后端的对比（NPU 950 MHz + DDR performance + CPU performance）：

| 阶段 | rknnlite | 零拷贝 |
|---|---:|---:|
| 预处理 | 1.26 ms | 1.20 ms |
| 绑输入 | 4.55 ms | 0.00 ms |
| 推理 | 21.73 ms | 21.76 ms |
| 取输出 | 4.73 ms | 0.30 ms |
| 解码 | 0.78 ms | 0.78 ms |
| 合计 | 33.05 ms | 23.92 ms |

省下的 9.1 毫秒分成两半：6.1 毫秒是甩掉 rknnlite 包装本身，2.1 毫秒是绑输入
（`rknn_inputs_set` 这一段直接消失），1.0 毫秒是绑输出。生产入口用
`--zerocopy full`，检测段 24.8 毫秒，帧率 30。

零拷贝后端有几条硬约束：初始化 flag 必须是 0（不要加那两个 flush cache 的位），
绑输入要求原生布局和紧凑布局一致，原生和逻辑输出的属性必须一致，`is_prealloc=1`
时 `size` 也必须填（漏填输出恒为零）。另外它只在 640×480 上成立，因为模型的静态
输入是 480×640，letterbox 恰好是恒等变换；换分辨率要重新导出模型。

## 二、三段改造与全链折算

把预处理、绑输入、渲染三段分别改过一遍，在一个循环里实测（1 人 / 3 人，毫秒）：

| 配置 | 1 人 | 3 人 |
|---|---:|---:|
| 原样（float32 预处理、老绑输入、带渲染） | 63.79 / 15.68 fps | 67.35 / 14.85 fps |
| 改预处理 + 绑输入 | 39.98 / 25.01 fps | 43.45 / 23.01 fps |
| 再加渲染改造 | 36.70 / 27.25 fps | 36.74 / 27.22 fps |

加上编码 2.15 毫秒和时序模型的摊薄，折算到整条链路，对着 21 fps 的门看：

- 三项都不改：1 人 14.15 fps，3 人 13.47 fps，都不过。
- 只改预处理和绑输入：1 人 21.34 fps 过，3 人 19.87 fps 不过。
- 三项全改：1 人 22.95 fps，3 人 22.93 fps，都过，余量只有 1.93 fps（9%）。

渲染那一项是 3 人场景过门的必要条件：老的渲染器每人做一次整帧拷贝，
1 人 3.34 毫秒、3 人 6.77 毫秒；改成一帧只拷贝一次、画布跨帧复用之后，
整帧拷贝只有一次。

预处理从 11.06 毫秒降到 3.62 毫秒，用的是一条 256 项的查表加 `cv2` 的 `dst=`
就地转换；`set_inputs` 从 32.16 降到 1.717 毫秒。

## 三、锁频与核分配

三处都要锁，缺一处结果就不可比：NPU `userspace/950000000`、DDR
`performance/2736000000`、CPU 全核 `performance`。三项都回读校验。不锁 CPU 时
结果会偏慢 1.45 到 13.9 倍，而且越靠后端的阶段被放大得越狠。

以前有一条结论说"不锁 DDR 会让推理慢 80%"，后来被推翻了：三锁之下 DDR 534 MHz
和 2736 MHz 的推理耗时都是 17.5 到 17.9 毫秒。DDR 的作用是在别的环节。

NPU 只有两个核，`CORE_2` 会被运行时静默换成 `CORE_0`，`CORE_0_1_2` 换成
`CORE_0_1`，"三核"是不存在的。分核收益：检测器单核 63.38 毫秒、双核 59.42 毫秒
（1.07 倍）；时序模型反过来，单核 54.70 毫秒、双核 64.91 毫秒（0.84 倍），
因为它图太小（364 个节点、125 个卷积），双核的调度开销比收益大。所以生产是
检测器绑 `CORE_0_1`，时序模型绑单核跑。

两个进程分核并发是有效的：串行 14799 毫秒，检测器跑 `CORE_0`、时序模型跑
`CORE_1` 时 7871 毫秒（1.88 倍），同核并发只有 1.12 倍。说明两个核确实独立。

CPU 亲和性也要管：预处理单线程在 A53 上是 31.19 毫秒，在 A72 上是 13.91 毫秒，
差 2.24 倍。管线线程必须留在 A72 那四个核上。

一个坑：三个 RKNN 会话同时推理会把 NPU 挂死（job timeout 之后无限 soft reset，
当时整机重启了 4 次），所以同时最多两个会话。同一个会话也不能两个线程共用，
runtime 有全局锁，每个线程要各建一个实例。

温度方面，满载 40 秒时 npu-thermal 34.2 度、soc-thermal 32.4 度；另一轮冷机实测
26.8 到 28.7 度。没有出现过降频。

## 四、时序模型的耗时

ST-GCN++ 每窗跑一次，输入是 `(1,1,64,17,3)`，耗时随人数线性增长：

| 人数 | 单次耗时 |
|---|---:|
| 1 | 57.51 ms |
| 2 | 114.92 ms |
| 3 | 171.69 ms |

每窗预算是 500 毫秒，三个人的 171.69 毫秒有足够余量。真正麻烦的是它跑在消费者
线程上会把主线程钉住 57 到 172 毫秒，这段时间相机出的帧只能丢。

改成后台线程打分之后，相机取帧率 1 人时从 26.60 到 27.03（+1.7%），
2 人从 27.00 到 28.00（+3.7%），3 人 26.70 到 27.65（+3.6%）；按臂汇总丢帧率
从 10.8% 降到 7.7%。生产日志里按紧邻窗口复核，1 人 +0.9%、2 人 +4.2%、3 人 +3.6%，
与交替 A/B 的结果对得上。可引用的口径就是 1 人约 +1%、2 到 3 人 +3.5 到 4%。

早期有一版记的是 +7%，那个数字已经作废：两臂都漏了核分配的参数，跑在 NPU 自动
调度（单核）上，而且满机生产是 26.8 fps 不是那时记的数字。

异步必须逐位等价才敢上线。验证用 `board/p8/verify_async_parity.py`：PC 合成场景，
假分数由输入张量本身算出来，比较逐窗、逐人、事件、计数、窗口人数等全部字段，
不做容差。四个场景（单人 / 3 人封顶 / 有空洞 / 慢队列）PC 和板端各 4/4 通过、
逐位相同；异步下 36/37 个窗迟到，最多迟 15 帧（一个步长），同步全是 0。
板端拿 19 条视频做 A/B，异步那趟和同步那趟 20 个产物逐位相同。

队列满时的策略是阻塞，绝不丢窗。丢一个窗会让窗口分数记成 0.0，而 0.0 和"模型
很确定没跌倒"是同一个形状，会污染状态机。

## 五、RTSP 推流链路

管线是 `v4l2src`（mainpath，io-mode=2）出 NV12，直接进 `mpph264enc`（CBR），
过 `h264parse` 和 `rtph264pay`。不加 `videoconvert`：源本来就是 NV12，编码器直接
吃得下，转换一次要多花 2.34 毫秒一帧。板上也没有硬件缩放元素
（`rkvideoscale`/`rgaconvert`/`rga` 都不在），软件 `videoscale` 是 6.3 毫秒一帧，
所以要标清就让 ISP 直接出 640×480，不要缩。

1080p 实测 30.24 fps，码率 3.65 Mbps；三个客户端同时拉流是 30.3/30.1/30.2 fps，
服务器 CPU 12.2%，和单路持平（一份编码多路分发）。纯硬编的吞吐是 464 fps
（2.15 毫秒一帧）。延迟用把序号编进画面左上角 8 像素的办法测过，640×480 文件源
是 p50 168 毫秒、p95 202 毫秒；1080p 那一轮测到 p50 52 毫秒。两轮测法不同，
引用时要说清是哪一轮。之前 MJPEG 直播的延迟是 p50 1796 毫秒。

带宽换编码器很划算。同一帧公平对比：MJPEG q70 是 28349 字节，H.264 CBR 1 Mbps
是 3958 字节，差 7.16 倍；换一条画面复杂的录像差 5.18 倍，蹲姿那条差 9.06 倍。
所以 MJPEG 和 H.264 的实际差距在 5.2 到 9.1 倍之间。

码率控制的精度：设 500/1000/2000 kbps 实测偏差在 -2.0% 到 -2.5%；
设 4000 kbps 实测只有 3305（-17.4%），这一档不准，要用就先核对。

`appsrc` 喂帧实验出了个反直觉结果：`Buffer.new_wrapped` 的零拷贝路径 p50 是
130.54 毫秒（上限 7.6 fps），而 `new_allocate` 加 `fill` 的拷贝路径只要 7.98 毫秒
（上限 123 fps），零拷贝反而慢 16 倍。所以喂帧一律用拷贝路径。

另外测过一个原型：在检测进程里顺带用 Python 喂帧推 640×480，带检测时 10.8 fps、
首帧 239 毫秒，不带检测 20.5 fps。结论是这条路线撑不到 30 fps，生产才改成推流端
独立采 mainpath。

## 六、已经作废的数字

2026-10-25 那一轮资源画像用的不是生产模型：当时板上的生产检测器是 INT8
320×320（307 KB），分类器 INT8 224×224（150 KB），而那一轮测的是 FP16 的
480×640（1.84 MB），数据量差 6 倍。那一轮的所有绝对毫秒数和由它推算的帧率都作废，
包括"零拷贝能省 36 毫秒"和"生产模型 `set_inputs` 要 32 毫秒"这两条——
生产 INT8 实测只要 0.20 毫秒，零拷贝反而慢 1.3 到 2.2 毫秒。

那一轮仍然有效的部分：硬件底账、分核实验（1.07 倍 / 0.84 倍）、并发实验（1.88 倍）、
A72 对 A53 的 2.24 倍，以及三条测量陷阱。

还有一批作废的：`board/p8/p8_zerocopy.c` 早期 G1–G4 那四组对照，以及由它推出的
所有排序。根因是 `is_prealloc` 从来没设过，而且 `rknn_inputs_set` 被放在计时区
外面，漏算了 15.59 毫秒。修正后的正确排序是 `ap` < `a` < `b`，且都远快于 `b0`。

另外有一类不可引用的差异：推理耗时有双峰现象（低档 14.28、高档 17.4 到 17.8，
极差 19.9%）。所以段与段之间 5 到 18 倍的差异可以引用，两个模式之间小于 2 毫秒的
差异分辨不出来；想说"A 比 B 快 X 毫秒"而 X 小于 3.5 时，必须跑够 10 个进程。

## 七、取舍

零拷贝后端加 float16 直通：换来的是检测段 33.0 到 23.9 毫秒、整机 30 fps。代价是
它们只在 640×480 的输入上成立，换分辨率必须重新导出模型；预处理也只覆盖了
letterbox 恒等那条快路径，插值那条一般路径没有测试覆盖，接分辨率不同的相机时要
补逐像素对拍（Python 缩小用 `INTER_AREA`，C 侧只有 `INTER_LINEAR`）。

三处锁频：换来的是帧率确定、结果可复跑。代价是功耗与发热按满频走。检测器绑双核、
时序模型绑单核的分法来自实测（检测器双核 1.07 倍，时序模型双核反而 0.84 倍），
是这块板卡上的结论，不是通用规律。

后台线程打分：换来的是 2 到 3 人场景 +3.5% 到 4%，丢帧率从 10.8% 降到 7.7%。
代价是这套验证只覆盖到 3 人，4 人以上没有数据。

上面那张全链路折算表不含解码（9 个张量还原成框和关键点）、视频解码、告警的 JPEG
编码与共享内存推送。表里时序模型的摊薄按 4.73 毫秒一帧算，按真实管线实测是
7.156，所以实际余量比表里写的更紧。温度只测过冷机首小时，连续运行是否降频没有数据。
