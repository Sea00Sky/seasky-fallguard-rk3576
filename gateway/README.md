# FallGuard 边缘网关

板端感知进程判定完一个窗口，就把事件写进一块 POSIX 共享内存；本目录的 C 程序
是这块内存的消费者：取出事件落进本地 SQLite，按闸门推给护士站，同时对外提供
查询接口和告警快照。

它跑在 RK3576 上，和感知进程是两个独立进程，共用一块内存，不通过网络通信。
感知进程重启不影响已落盘的事件，网关重启也不会丢事件环里还没取走的那几条
（环在 `/dev/shm`，两侧都重启才清空）。

## 为什么中间加一层

感知进程直接把事件 POST 给云端也能跑，但把推送放在本地网关有三个好处：云端不可达
时检测不受影响，事件先在本地落盘、恢复后按队列补推；网络抖动不会被当成判定失败；
护士站地址变了只改网关配置，不用动推理进程。

代价是多了一个共享内存契约要维护，结构体一改两侧必须同时重启，见下面那条版本约束。

## 共享内存契约

契约在 `edge_gateway/include/fallguard_shm.h`，Python 侧的 `shm_proto/shm_ipc.py`
是它的逐字段镜像。三个结构体的大小和每个字段的偏移都在两侧各有断言：C 侧是编译期
静态断言，Python 侧在导入时校验。尺寸或偏移对不上就不是警告，是直接拒绝启动。

- 头：magic `0x4647414C`、版本号、本端认为自己应有的尺寸，读侧按
  magic → 版本 → 尺寸 三查，任何一项不符就退出。
- 事件 144 字节，环形队列 32 条，满了覆盖最旧的一条。
- 告警快照双缓冲，各 200 KB JPEG 上限加 16 字节帧头，写一读一交替。
- 整块 414344 字节。
- 三个信号量：互斥、事件到达、帧更新。v3 起没有直播帧，第三个已经没有人投递，
  名字保留是为了不破坏还在打开它的旧脚本。
- 事件字段：序号、时间戳、人员号、类别、置信度、检测框、融合分数、判据文本、
  快照序号、状态、窗口起止、跌倒概率、覆盖率、模型版本。
- 状态是三态：疑似、确认、撤回。护士端把「红卡转灰」就靠这个字段，缺了等于没有撤回。

版本约束值得单独说：v2 到 v3 换了结构体布局，整块从 820320 字节缩到 414344 字节。
读侧的 `fstat` 只能查出「太小」，查不出「太大」——一块残留的旧内存会顺利通过尺寸
检查，真正拦住它的是内存内部记录的尺寸三查。所以升级要同时重启两侧并先删掉
`/dev/shm/fallguard_shm`，或者交给写侧：写侧有重建权，发现尺寸不符会自己重建。

## 五个线程

1. 监听：等事件信号量（带 500 毫秒超时兜底），醒来后把环里的事件一次取空、逐条
   放进进程内队列。醒来不等于只有一条，所以取事件是循环。
2. 推送：从队列取出，写 SQLite，过闸门，POST 给护士站，回写推送结果。
3. HTTP：监听、接连接，每个连接起一个 detached 线程处理。
4. 配置：inotify 盯配置文件，变更时写回共享内存配置区，感知侧读走。
5. 看门狗：定时向 systemd 报活。

看门狗那部分是三十行自己实现的 `sd_notify`，只往 `$NOTIFY_SOCKET` 这个 unix 数据报
socket 发一行 `KEY=VALUE`，不引 systemd 的开发库。没有它就不能开 `WatchdogSec=`，
开了而从不报活会被 systemd 无限重启。

连接线程的栈单独调到 512 KB。每个连接一个线程，用默认的 8 MB 栈，32 个并发就要
256 MB 虚拟地址；512 KB 仍然放得下栈上那个 200 KB 的快照缓冲和请求缓冲，余量约
300 KB，所以再加大的局部数组之前先改这个数。并发连接数有上限，超了直接关闭，
读请求有超时，半开连接不会一直占着线程。

## 落盘与幂等

SQLite 单文件加一个快照目录，目录由配置指定。数据库是惰性打开的：启动时数据目录
可能还没挂好，所以每次读路径也会补开一次，库恢复后接口不再报 503。

幂等键是「人员号、窗口起点、模型版本」三元组，落在一条部分索引上。两个选择都是
踩过坑才定的：

部分索引（`WHERE window_start > 0`）——上游没填窗口号的事件窗口起点是 0，普通索引
会把它们全部当成同一个键，不同事件互相顶掉。

非唯一索引——窗口起点是「进程启动以来的帧号」，感知进程一重启就从 0 重新数，不同
会话的两次真实跌倒可能落在同一个键上。这里用唯一约束会把第二次插入直接拒掉，只能
退回「更新旧行」，等于新告警被旧卡吃掉，是漏报。所以幂等由写入函数显式判定，索引
只加速查找。

撤回是第二次投递，走的是「按身份键找到原行、原地更新状态」这条路，不新增一行。
老库升级靠逐列 `ALTER`，重复执行时报「列已存在」是已迁移过，不是错误。

## 推送闸门

四道顺序判断：总开关、状态、冷却时间、接收地址是否配置。

状态闸门只放行确认和撤回两态，疑似不推。冷却只约束确认——撤回是更正，不是新告警，
被冷却窗口吞掉的话「先红卡、后灰化」就永远发生不了。

分数闸门已经删掉。融合分数和上游判定用的不是同一个口径，真机上复现过「上游已经判
FALL、网关按分数拒」，结果真摔一条都没送达。上游的判定已经把所有该拒的分支拒过一遍，
决策只做一次；配置区里的阈值字段还在、护士端也还在读，但它不再参与推送判定。

冷却用单调时钟，不是墙上时钟。NTP 校正会让两次推送的时间差变成负数或突然变大，
用墙上时钟会出现「冷却变成三十年」或者冷却直接失效。

## HTTP 接口

只支持 GET，一共三个：

| 路径 | 返回 |
|---|---|
| `/api/status` | 网关与感知进程的状态、事件计数、配置区现值、环形队列条数与推送队列深度 |
| `/api/events` | 最近若干条事件的 JSON 数组，条数用查询参数指定 |
| `/api/snap` | 最新一条告警快照的 JPEG，还没有快照时返回 404 |

`/api/live` 与 `/api/live.mjpg` 从 v3 起返回 410。直播帧已经不在共享内存里，
画面改由感知进程的进程内 MJPEG 或 RTSP 承担，网关只做事件、快照、状态。
用 410 而不是 404 是为了让还指着这里的老客户端停止重试。

接口本身不做鉴权，设计上只在设备所在的网络内提供；要往外开得自己加一层。状态接口
还会回显网关自己配置的推送地址和数据目录，所以它不适合直接挂到公网。

## 配置

`config.json.example` 是完整字段列表，复制成 `config.json` 后按现场填。字段包括
共享内存名、HTTP 监听端口、灵敏度档位、推送阈值、推送冷却、推送开关、接收地址、
数据目录。

灵敏度是给护士端看的档位标签（低、中、高三档），真正参与推送判断的是状态、冷却时间
和总开关；阈值字段随档位一起下发，但如上一节所说，它已经不参与判定。接收地址和
数据目录属于网关本地项，不进共享内存契约；其余字段会写进配置区供感知侧读取。

## 构建与运行

```bash
cd gateway/edge_gateway
make
./fallguard-gateway --config config.json
# 需要装到系统路径时再 make install
```

只依赖 libc、pthread 和 sqlite3。SQLite 头文件随仓库放在 `third_party/`，
链接时按本机已有的 `libsqlite3.so` 版本走，不要求开发包。日志走 syslog，
`journalctl -u <服务名> | grep METRICS` 能看到一行运行指标。

## 验收与模拟

不用相机、也不用推理，就能验证共享内存这一段。`sensor/mock_fall_generator.py` 按
`tests/scenario_hospital_ward.json` 写共享内存，支持加速回放、保留或清理内存；
写读自检可以用 `--self-test` 单独跑。`scripts/verify_p1.py` 回放整份场景后把内存
读回来，逐字段核对事件内容、环形队列的读写指针与幸存条数、状态区与快照序号，
全过打印 PASS。

`shm_proto/dump_shm.py` 是只读诊断，用来在板上直接看内存里现在是什么。
共享内存相关的验收脚本都在 PC 上也能自跑，不需要板子。

## 取舍

共享内存加本地落盘：换来的是断网不丢事件、云端不可达不影响检测，以及推送目标
可改。代价是要维护一份两侧逐字段对齐的契约，改结构必须同时重启并清内存。

进程内队列满时丢最旧的一条并计数：换来的是推送线程卡住不会把监听线程一起拖死。
代价是极端情况下会丢事件，只能靠日志里的指标行发现，所以丢弃计数和闸门挡掉的条数
每十秒打一行。

配置热更新走 inotify 监听文件：换来的是改灵敏度不用重启，判定不停。代价是配置
只支持扁平的键值 JSON，嵌套结构要自己扩解析。

网关只做事件与快照，不转发视频：换来的是省掉了 MJPEG 长连接这一类最容易泄漏线程
的地方。代价是看实时画面要另外连板端的直播端口或 RTSP，不能只开一个网关端口。

推送闸门放在本地网关：换来的是断网时不会攒下一堆重复推送，恢复后按顺序补发。
代价是冷却节奏和云端的事件处置节奏要一起调，改一处要想起另一处。
